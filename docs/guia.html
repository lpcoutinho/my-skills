Duas formas de chamar

você digitaSó roda quando você digita o nome. O agente não chama sozinho, e outra skill também não. Quase todo o ciclo SDD é assim: você decide quando cada fase começa.
automáticaVocê pode digitar, e o agente também chama sozinho quando a tarefa combina com a descrição (“debuga isso” aciona diagnosing-bugs). Outras skills também chamam essas.

Na maioria dos agentes o comando é /nome. No Codex, mencione a skill com $nome. As skills ficam instaladas por symlink a partir deste repositório, então não existe o prefixo mattpocock-skills: do plugin: é /to-spec, /implement e assim por diante.

O code-review do Matt foi instalado como mp-code-review, porque o Claude Code tem um /code-review próprio e diferente. As skills do Matt que chamam a revisão (implement, implement-spec) já apontam para o nome novo.

O ciclo SDD com as skills do Matt

Spec-driven development, aqui, quer dizer: nenhuma linha de código antes de o plano estar fechado e escrito num lugar que o agente consulta. As skills do Matt dividem isso em fases, cada uma com uma saída concreta (um glossário, uma issue, um ticket, um commit). A saída de uma fase é a entrada da próxima.

  1. /setup-matt-pocock-skillsuma vez por repositório

    Olha o repositório e pergunta, uma seção por vez: onde ficam as issues (GitHub pelo gh, GitLab pelo glab, arquivos em .scratch/ ou outro que você descrever), se mantém os labels de triagem padrão e onde ficam o glossário e os ADRs. Mostra o rascunho antes de gravar.

    Saída: docs/agents/ (issue-tracker.md, domain.md, triage-labels.md) e um bloco ## Agent skills no CLAUDE.md ou AGENTS.md. Faça o commit.

    /setup-matt-pocock-skills
    /setup-matt-pocock-skills usa issues locais em .scratch, é um projeto só meu
  2. /grill-with-docsalinhar: o plano ainda está vago

    Te entrevista em rodadas até vocês dois terem o mesmo entendimento. Por baixo, chama grilling (a entrevista) e domain-modeling (a linguagem). Termos novos vão para o GLOSSARY.md na hora; decisões difíceis de reverter viram ADR.

    Saída: GLOSSARY.md, docs/adr/ e o plano fechado na conversa.

    /grill-with-docs quero que o gestor exporte os pedidos do mês em CSV
    /grill-with-docs como deve funcionar o cancelamento de uma assinatura no meio do ciclo?
  3. /to-specespecificar: decisões tomadas, trabalho de várias sessões

    Não entrevista: só registra o que já foi decidido. Antes de escrever, propõe os seams onde a feature será testada (de preferência um só, no ponto mais alto possível) e confirma com você. A spec tem problema, solução, user stories, decisões de implementação e de teste, e o que está fora do escopo. Sem caminhos de arquivo nem código.

    Saída: uma issue no tracker com o label ready-for-agent.

    /to-spec
    /to-spec o mapa do wayfinder fechou, a decisão está em "Formato do CSV"
  4. /to-ticketsfatiar em tracer bullets

    Quebra a spec em tickets verticais: cada um atravessa todas as camadas (schema, API, UI, testes), cabe numa janela de contexto e pode ser demonstrado sozinho. Cada ticket declara quais outros o bloqueiam. Mostra a lista numerada e pergunta se a granularidade e os bloqueios estão certos antes de publicar.

    Saída: uma issue por ticket, publicadas na ordem das dependências; no tracker local, .scratch/<feature>/issues/NN-slug.md.

    /to-tickets #34
    /to-tickets o plano está nesta conversa
  5. /implement ou /implement-specconstruir

    /implement pega um ticket, roda tdd nos seams combinados, typecheck e testes, chama mp-code-review e commita na branch atual. Um ticket por sessão, com o contexto limpo entre eles.

    /implement-spec pega a spec inteira: cria uma branch de integração, roda um subagente por ticket desbloqueado, cada um no seu worktree, junta tudo e roda uma revisão no fim. Abre PR em rascunho se o tracker fecha trabalho por PR.

    Saída: commits na branch atual, ou uma branch de integração com todos os tickets.

    git switch -c feat/export-csv
/implement #35
    /implement-spec #34
  6. /mp-code-reviewrevisar contra um ponto fixo

    Já roda dentro do implement, mas vale chamar sozinho antes do PR. Revisa o diff desde um ponto fixo em dois eixos, cada um num subagente: Standards (segue os padrões documentados do repo e uma lista de code smells do Fowler?) e Spec (faz o que a issue pediu?). Acha a spec pelas referências nos commits.

    Saída: dois relatórios lado a lado. Não caça bugs de baixo nível: para isso, use o /code-review nativo do Claude Code.

    /mp-code-review desde main
    /mp-code-review desde HEAD~3, a spec é a issue #34
  7. /prentregar

    Escreve o corpo do PR em três partes: Summary (o menor visual que explica a mudança: pseudocódigo, árvore, diff resumido), Evidence (antes e depois) e Merge Danger (dá para voltar atrás? até onde quebra se estiver errado?).

    /pr escreve o corpo do PR desta branch
  8. /retroaprender: depois de uma sessão difícil

    Lê a sessão e sugere mudanças no ambiente, não no código: um ponteiro de navegação no AGENTS.md, um check automático, uma regra nova para o revisor, uma instrução que não muda nada e pode sair. Só propõe; você escolhe o que aplicar.

    /retro
    /retro o agente levou muito tempo para achar onde ficam as migrations

O ciclo fecha aqui: o que o /retro mudar no ambiente vale para o próximo /grill-with-docs. Mantenha as fases 1 a 3 (grill, spec, tickets) numa mesma janela de contexto, sem limpar nem compactar, para tudo partir do mesmo raciocínio. Cada /implement começa limpo, a partir do ticket.

Cabe numa sessão?

Pule spec e tickets: /grill-with-docs e depois /implement na mesma janela, dizendo que o plano está na conversa.

Grande e nebuloso demais?

Comece por /wayfinder. Ele monta um mapa de tickets de decisão no tracker e resolve um por vez. Quando o caminho clarear, volte ao ciclo pelo /to-spec.

Uma pergunta que conversa não resolve?

Desvie para prototype: código descartável numa branch própria. Olhe, responda e volte com o que aprendeu (/handoff leva o contexto nos dois sentidos).

Depende de fora?

Fato externo (API, versão, spec de terceiros): research. Decisão de outra pessoa: /to-questionnaire. Chegaram issues de outras pessoas: /triage.

Armadilhas conhecidas

implement commita na branch atualEle não cria branch nem pergunta. Crie a branch antes de rodar.
to-spec marca ready-for-agentUm agente autônomo que procura esse label vai tentar construir a spec inteira. Se você vai trabalhar por tickets, tire o label da spec depois do /to-tickets.
grill-with-docs pula o glossárioÀs vezes só a entrevista acontece. Se o GLOSSARY.md não mudou no fim, chame domain-modeling.
Fatiar por camada“Só o backend” e “só o frontend” não são tickets do /to-tickets: cada ticket atravessa todas as camadas. É a hora de reclamar, antes de publicar.
tdd em código sem regraEm config, cola ou CRUD puro, o teste vira cópia da implementação. Combine os seams na spec.
research roda em segundo planoEle sobe um agente separado. Confira duas ou três citações do resultado: se caem num resumo e não na fonte, a pesquisa falhou.
prototype parece o próximo passoSe você já sabe o que construir, é /implement. Protótipo responde pergunta; não vira código de produção.
Skills vendored não se editamAs do Matt e o humanizer são cópias do upstream: o make update sobrescreve. Para mudar o comportamento, crie outra skill.

Fim de fase: o que fazer com o contexto

Na ordem em que o ask-matt sugere avaliar:

OpçãoQuando
ContinuarA próxima fase precisa desta conversa literalmente (grill → spec → tickets). Descarte esta opção primeiro.
/clearNada daqui importa para o que vem: entre um /implement e outro.
/handoffO trabalho vai para outra ferramenta, outro diretório, outra pessoa, ou uma tarefa paralela. Grava um markdown portátil na pasta temporária.
SubagenteUma tarefa bem delimitada que roda na própria janela e devolve um relatório.
/compactNenhuma das anteriores. É o padrão, mas a última a considerar.

Fontes: os SKILL.md de cada skill em skills/. Skills do Matt: github.com/mattpocock/skills. Humanizer: github.com/blader/humanizer.
